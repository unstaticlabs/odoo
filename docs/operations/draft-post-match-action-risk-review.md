# Draft-bill posting and matching: action review

The new preview reads the caller's eligible payment, posting date and confirmation facts. It requires the bill's native write and posting rights because it previews a workflow the caller may execute. It does not save a bill, allocate a journal number, change a bank statement or create a reconciliation. The persistent-write rejection test and independent HTTP preview/Cancel snapshots prove this distinction. The private eligibility helper is named `_check_draft_match_candidate` to describe its actual read-only purpose; the inventory's conservative substring heuristic previously treated `_post` in its name as a write. No discovery rule or native permission changed.

`get_draft_post_match_preview` is read-only. `js_post_and_match_outstanding_line` is an operational workflow: it rechecks the current draft bill, company, write rights, eligible posted payment and reviewed facts under native record locks, then delegates to native posting and matching. It has no sudo, provider call, arbitrary model or code execution, explicit transaction commit, or client retry. Native accounting and irreversible-action boundaries continue to govern the delegates.

A posting failure leaves the bill draft. A later matching failure rolls back the matching savepoint and returns an explicit posted-but-unmatched outcome, retaining the posted bill and its audit trail. The user may continue the native matching workflow after checking current state. Success creates one posted bill and one native reconciliation, attributed to the caller, with the original bank date, amount and reference preserved. Two simultaneous requests produce one successful posting and one native stale/lock rejection, rather than duplicate postings.

Automated evidence lives in `custom-addons/usl_accounting/tests/test_immediate_settlement.py::TestImmediateSettlement`, including preview persistent-write rejection, user-specific suggestions, read-only and selected-company denial, stale line edits without parent timestamps, explicit confirmation, posting failure, late matching rollback, successful posting/reconciliation and duplicate request rejection. Desktop and mobile HOOT tests cover the confirmation, cancellation, pending state, known-result refresh errors and uncertain RPC recovery. Synthetic browser captures illustrate the reviewed layout; still images do not prove these behaviors.

Managed Agents use the existing JSON-2 authorization and operation-scope boundary. Native posting includes scoped supplier-rank and other framework side effects. The write-capable Agent test calls the maintained classifier/context helpers before the workflow and verifies posting, payment, reconciliation and Agent attribution without the irreversible-action group. The read-only Agent is rejected by the native classifier, and an unscoped sudo attempt remains denied without changing the draft or payment. No new collaboration token, generic wizard grant or permission bypass is introduced.
