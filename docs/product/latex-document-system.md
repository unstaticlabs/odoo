# Governed LaTeX document system

## Product commitment

Human-readable business PDFs generated by the Distribution use one governed
document system. The visual standard is global, not limited to Odoo: concise
language, embedded Lato typography, clear metadata, disciplined tables,
generous whitespace and restrained company branding. Templates are versioned
software, reviewed and released with the renderer; users cannot inject LaTeX
or edit production template source from Odoo.

The first production families are customer invoices and credit notes,
canonical accounting statements, official correspondence and Native Sign
completion certificates. Machine outputs (FEC, UBL/CII XML, CSV and XLSX),
incoming originals and third-party source PDFs remain native or passthrough.
Every installed report is classified accordingly.

## Architecture decision

Three credible paths were compared:

1. Odoo QWeb and wkhtmltopdf, which preserve native report behavior but make
   high-quality paginated typography and PDF/A consistency difficult;
2. OCA Py3o, which is LibreOffice-based rather than LaTeX-based and is not the
   canonical OCA 19 rendering path for this Distribution;
3. governed Odoo adapters plus an isolated, allow-listed LaTeX renderer.

The third path is selected. Covered report actions remain `qweb-pdf`, so Odoo
continues to own access checks, filenames, batching, attachment reuse, mail,
portal delivery and localization hooks. Only actions with an upgrade-managed
template binding are intercepted. An unhealthy renderer or incomplete company
identity blocks a new official render with a Settings link; there is no silent
QWeb fallback. Existing immutable attachments remain available.

The renderer accepts normalized JSON and content-addressed image assets only.
It has no raw-LaTeX or template-path input, no runtime network access and no
durable document cache. A pinned image runs as a non-root user with a read-only
filesystem, bounded tmpfs, dropped capabilities, request/concurrency/time
limits and mutual TLS on an internal network. Logs contain request identity,
template revision, payload digest, duration and outcome, never document text.

## Company and legal identity

Native company logo, address, VAT, registry, APE code, language, colors and
paper format remain authoritative. The shared add-on adds only legal form,
share capital and RCS city where Odoo has no governed equivalent. Readiness is
computed per company and covered documents resolve their company from the
business record, not merely the active UI company.

French invoice adapters validate the recipient address, invoice date and
late-payment/recovery wording before rendering. For the 1 September 2026
French rollout they also print the customer SIREN, a distinct delivery
address, the goods/services nature of the transaction and the VAT-on-debits
option when the native tax configuration establishes it. Official correspondence
snapshots the sender, recipient, legal identity, body, signatory and attachment
list at finalization. Corrections create a superseding version instead of
mutating an issued PDF.

## Output and provenance

All PDFs are searchable, Unicode-extractable and use embedded fonts. Official
letters, accounting statements and Sign completion certificates validate as
PDF/A-2b. Invoice output is a Factur-X-compatible visual base; Odoo retains its
native XML embedding and PDF/A-3 post-processing.

Template key and revision, canonical payload SHA-256, renderer version,
company and render time are stored on durable Odoo attachments. The same
template revision is embedded in PDF metadata and response headers. Release
checks reject an absent, dirty, non-HTTPS or incorrectly pinned renderer
submodule.

## Release boundary

Native Sign is a hard merge gate. `sign_completion.v1` exists and is visually
qualified in the renderer package, but the Odoo Sign adapter is added only
after the Native Sign feature lands on `19-usl`, when its real evidence,
validation and archival contracts can be tested. A speculative certificate
adapter is not a substitute.
